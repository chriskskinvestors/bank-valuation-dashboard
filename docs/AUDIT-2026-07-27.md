## LIVE INCIDENT — refresh-home-snapshot: ROOT CAUSE CONFIRMED (task-timeout kill)

Since **2026-07-27 00:05 UTC (Sat 2026-07-26 8:05pm ET)** every execution of
the `refresh-home-snapshot` Cloud Run job fails (~2 alert emails per 30 min).
Confirmed 2026-07-27 from the execution logs (via the owner's signed-in console
session):

- The job's schedule is now every 30 min (:00/:30); each failed run is killed
  at exactly its **1800s task timeout** ("Terminating task because it has
  reached the maximum timeout of 1800 seconds", e.g. execution
  `refresh-home-snapshot-mmmwp`, 12:00→12:32 ET).
- Phase timings prove where the time goes: `load_fdic: 1s / load_sec: 1s /
  load_prices: 0s` (warm caches), then **`build_all_bank_metrics` runs >29 min
  and never finishes**. The one success of the day (6:00 AM ET,
  `…-7nfnp`) logged `build_metrics: 905s` — even the BEST case is ~15 min,
  and daytime runs exceed 30.
- Why the "compute" step does network I/O: `compute_all_valuations` resolves
  per-bank as-reported TBVPS via `data/sec_earnings_8k.py` (EDGAR 8-K index +
  EX-99.1 + XBRL anchor fetches) and `data/otc_release.py` (wire/IR-site
  crawls). Both read their caches with bare `cache.get()` → the **24h ceiling
  (finding P2 #4's class) silently voids their by-design-immutable
  per-accession caches every day**, and `reported_tbvps` additionally folds the
  changing reconstruction/bvps anchors into its key. 538 banks × several
  EDGAR requests under the shared SEC rate limit = a 15–30+ min build,
  slowest when EDGAR/daytime contention is highest. Q2 earnings-week release
  volume pushed it over the 1800s cliff Saturday evening; the quiet 6:00 AM
  window is the only run that still fits.
- Prior sporadic failures (07-20 1×, 07-23 3×) were the same mechanism at
  lower volume. NOT deploy-related (last deploy 07-24 16:14 ran clean 2+ days).
- Impact while failing: `watchlist_metrics_snap` ages; past the 6h TTL
  (`app.py:704-718`) cold Home loads pay the 60s+ inline rebuild. The news
  feed is unaffected (its warm runs first, inside the first minute — visible
  in every failed run's log). Degradation, not wrong numbers.

### RESOLVED — and what the measurements actually showed

1. **Mitigation (applied 2026-07-27 13:05 ET, console):** task timeout
   1800s → 3600s. **This is what ended the incident.** Every run since 13:30
   has completed — 13 consecutive successes, zero alert emails.
2. **Cache-ceiling fixes (commits f0063e6 + fd97ae7, deployed #922/#923
   green):** the accession-keyed earnings-8k / otc_release / release_metrics
   caches and the M&A-layer reads now pass `max_age_s=None`, and
   `_latest_earnings_8k` caches its per-CIK submissions lookup 2h. Correct
   and worth keeping — they stop a full daily re-extraction of every bank's
   release and the nightly M&A re-fetch storm.
3. **HONEST RESULT: those fixes did NOT measurably speed up the build.**
   Measured `build_metrics`, same 538 banks: 1545s / 1597s BEFORE, then
   1776 / 1849 / 1568 / 1661 / **201** / 1670 / 1639s after. Unchanged
   within noise. My PR #9 rationale ("largest remaining contributor") was a
   hypothesis the data refutes — recorded here so nobody re-derives it.

### STILL OPEN (P1, perf) — the actual dominant cost

`data/release_metrics.py:717-733` `_current_accession` does an **uncached
per-bank fetch of the multi-MB EDGAR submissions JSON**, and it is called for
every bank whose cached entry is older than the 15-min `is_fresh(cached, 900)`
gate (`:774`) — i.e. essentially every bank on every run, because runs are 30
min apart. ~538 serialized multi-MB fetches ≈ the entire ~27-min build. Both
the pre-fix and post-fix code paths call it, which is exactly why the cache
work changed nothing.

The one **201s** run (18:02, vs ~1650s for every other) is the proof: when the
15-min gate HIT for most banks, `_current_accession` was skipped and the same
build finished in 3.4 minutes. Warm-cache compute is ~200s; ~1450s is this
fetch.

Candidate fixes (owner decision needed — this touches a documented timeliness
guarantee, see `:770-773`: the 15-min re-check exists so an earnings-morning
release isn't served a quarter late, the "C served its April release until
9:39 on Jul-14" incident):
  a. Share ONE cached submissions-index read per CIK (the 2h cache already
     added in `sec_earnings_8k._latest_earnings_8k`) with `_current_accession`.
     Collapses ~538 multi-MB fetches to ~0 on most runs. Timeliness for THIS
     path degrades to ≤2h — but `poll-events` already ingests 8-Ks every
     minute and invalidates fundamentals, so the guarantee lives there.
  b. Drive the re-check off the events store (one indexed query) instead of
     EDGAR — same timeliness, no per-bank network.
  c. Leave it: runs now fit comfortably in the 3600s timeout. Costs ~27 min
     of compute + heavy EDGAR load every 30 min, permanently.
Recommendation: (b), falling back to (a). Do NOT ship without measuring
`build_metrics` before/after — this section is what happens when you don't.

## P2 — fix soon (hand-verified ✓ where marked)

1. ✓ **OTC release cache version not bumped with shared-extractor fixes —
   bug-era wrong metrics stay pinned until the bank's next release (~Oct).**
   `data/otc_release.py:281` is still `otc_release:v6` while the shared
   extractor moved `release_metrics:v13→v16` (incl. the v15 "respectively-pair"
   fix that shipped CCFN ROE 1.70 vs real 14.65 on the SEC path). The file's
   own coupling comment (`:279-281`) requires the joint bump. Any OTC bank
   extracted 07-16→07-21 with "respectively"-form prose renders bug-era ROE/ROA
   labeled "per company release". **This is a rendered-wrong-number class —
   first fix in the queue: bump to v7 (one line) + rerun the job.**
2. ✓ **Results board masks total source failure as a confident quiet window.**
   `data/earnings_results.py:664-667` wraps `served_snapshot` in
   `except Exception: return []`; `served_snapshot` has no stale-serve on build
   failure, so a >15-min FMP calendar outage renders "No universe bank has
   reported…" (`ui/earnings.py:1805-1807`) — the AUDIT-2026-07-02 #34 class
   reintroduced on the new Results surface.
3. ✓ **Hollow deal-comps snapshot persists before the job's coverage gate.**
   `data/deal_comps.py:246` `cache.put`s inside the builder; the <100-deals
   gate (`jobs/refresh_deal_comps.py:64-69`) runs after, so a systemically-empty
   build clobbers the last good snapshot and `get_comps_snapshot`
   (`deal_comps.py:250-257`, no coverage check) serves it indefinitely while
   the job reports failure. The job's "previous snapshot still serves" log line
   is untrue for this branch.
4. **`cache.get()`'s 24h default silently voids the M&A layer's 7–90-day
   caches.** ma_history/ma_summary/offerings/stake_filings (7d),
   fdic_client RSSD lookups (30d), and ma_announcements' 90-day EDGAR doc-404
   negative cache all read with bare `cache.get(key)` (24h ceiling,
   `data/cache.py:61`), so the nightly deal-comps walk re-fetches its full
   EFTS + per-deal load every night (~7× designed EDGAR load) including
   known-dead documents — the 429-storm exposure class. Contrast
   `bank_universe.py:374` / `deal_comps.py:254` which pass `max_age_s=None`.
5. **Metrics snapshot lacks the stale-clobber guard its news-feed twin got.**
   `jobs/refresh_home_snapshot.py:178-182` writes `watchlist_metrics_snap`
   unconditionally with `cached_at` stamped at WRITE time; with the documented
   routine overlap, an older run finishing last overwrites fresher Movers data
   and it passes the app's freshness guard as new. The 2026-07-20 fix
   (`ui/home.py:813-824` build-start timestamp guard) was applied only to the
   news feed, six lines away from this write.
